## The molecule arrays live in clustercom

`naf`, `nal`, `nato`, `nmol`, `xadd`, `phix`, `tethered`, `mtype`, `moltype`, ... are in
`common.clustercom`, not in `molecom`. Map a routine's identifiers to modules using only the
includes that routine actually has. Two examples:

- `xmax`/`ymax` in readxyz are `plot_pars` COMMON, because readxyz includes plot_pars.inc.
- `ngrrot` in makelattice is a *local*, because makelattice does not `use molecom_mod`.

## cosd/sind: which one each object uses (decided from `nm` on the objects)

- makelattice.o and writexyz.o call `_gfortran_cosd_r4`/`_gfortran_sind_r4`, so the Python uses
  `cosd_intrinsic`/`sind_intrinsic`. The Rust writexyz uses EPSR's cosd, which happens to give
  the same results for the test angles.
- readxyz.o and plot3djmol.o declare them `external`, so the Python uses EPSR's
  `auxiliary_routines.cosd/sind/acosd/atan2d`.

## Quirks reproduced

### makelatticeato

The convert answer is parsed from the uninitialised `text`, not from `sometext`. The reference
stdout shows parse returning one word with `ncf(1)=1`, `ncl(1)=3020`, written as a 3034-character
line. The reason:

- `text` is character*256 of zero stack bytes (NULs, which are not blanks).
- parse is told `nstsize=3020`, so it reads on past `text` into more zero memory.

`text = '\0'*3020` reproduces this. As a consequence, `convert` compares the *whole* `sometext`
with `y`/`Y`.

The Rust port assumed a blank `text`. That gives the same files in ex38/ex39 but a different
stdout line.

### makelattice

`natomsph` is not declared, so it is an implicit INTEGER. `natomsph=1.0` stores the integer 1,
and ctype's REAL dummy receives its bit pattern, the denormal 1.4e-45. The Python passes
`int32(1).view(float32)`, as in the Rust.

Format 603 contains `13(/3(1x,f10.5))`, where the `1` is the continuation mark. The Python
format is `...',3(/3(1x,f10.5)))`.

### readxyz

- `yadd(ia)`, not `yadd(im)`, is read; the two are equal here.
- `ctype` is called with 11 of its 13 arguments: `natomsph=0.5*sigma`, `rhosph=1.0`,
  `radminsph=0.0`; `radmaxsph` and `pseudofacsph` are absent. This is the patched reference
  build (tools/build_patched_readxyz_readpdb.sh).
- If line 2 does not hold the cell, the stdin loop `do while(ierr.ne.0)` repeats forever at end
  of input, in both Fortran and Python.

### writexyz

- `natplot` is uninitialised when an empty append file is read. 0 is used, and any value except
  -2 takes the rewind branch.
- `ntag` is uninitialised but never used.
- The atoms of the central molecule are written even when their type is excluded. natplot does
  not count them.

### alignmole

- A rejected rotation "restores" the molecule from the work arrays `xr/yr/zr`, which are
  allocated but never assigned. The Python uses zero-filled arrays, as the Rust does; ex47/ex48
  never reject a move whose result matters.
- `niter < 10` makes `naccum = 0`, an integer division by zero: SIGFPE in the Fortran,
  ZeroDivisionError here.

### bondsclus

`bond(1,1)` of a one-atom molecule is never assigned (allocate gives garbage). Here it is 0.

### map3djmol

- `lendfirstdot` (sic) is assigned and `lenfirstdot` is tested, so `.cube` is always appended
  unless the name contains `.CUBE.txt`.
- `xcenterold`/`ycentreold`/`zcentreold` (sic) are never assigned but are written in the
  append-to-mol-cube branch. The Fortran wrote 0.00000000, so 0 is used.
- `nptrial` (sic) is unused.
- `rd(irmax)` is read with `irmax=0` when no maximum lies above rmin. The Python reads `rd[0]`,
  which is 0.
- phim/thetam/chim/thetal/phil/phi/chi start at 0.
- `call system(cmd,ierr)`: the GNU SYSTEM returns the raw wait status (for example 32512), but
  `runtime.system` returns the exit code. The Python converts it (code*256, or the signal number
  for a negative code).
- The Jmol launch goes through `runtime.system` with the Fortran's command string.
- A new-format plot3djmol input needs ncoeffs filled in. Otherwise `read(symbol_value,*) nexpan`
  fails with End of file in both versions, because `find_plot_par` runs only on the old-format
  path.

### concatenate with a literal nlast (read_plot3djmol, map3djmol)

`concatenate` assigns its `nlast` dummy. When the actual argument is a literal and
`nlast > nwords`, gfortran writes to read-only memory and the program segfaults.

The Python stops with `FortranStop(139, "Program received signal SIGSEGV ...")` at the same
calls:

- read_plot3djmol's `(2,4)` and `(1,2)` calls;
- map3djmol's spin `(1,1)` call when the value is blank.

The exit status matches. The tail of the Fortran stdout is lost in its buffer.

### setup_generic

- `ssg_ierr` is implicitly REAL but passed to an integer dummy. A nonzero integer has a nonzero
  bit pattern, so the test behaves the same.
- `ierrout` is uninitialised for epsr16/epsr17 (`setup_input_file` is skipped). 0 is used.

## read_plot3djmol is not in any active source

plot3djmol.f and setup_generic.f call `read_plot3djmol`, but no active file defines it. It
exists only in `plot_routines_g95.f` (line 2183), so these two programs cannot be linked from
the active sources alone.

The routine is translated on its own into `library/plot_routines_g95.py`. It calls the active
`plot_routines.find_plot_par`. The Fortran comparison build compiled the same lines (2183-2285)
as a separate object.

## Open issues (in other modules, not edited)

1. **`fortran/units.open` misses a gfortran OPEN rule.**
   - The rule: reopening a unit that is already connected to the same file, with a STATUS other
     than the connected one (and not 'old'), is an error, and the unit stays connected.
   - Effect: `plot_routines.save_plot_files` opens unit 14 with status='new'. `save_files_plots`
     then reopens it with 'unknown', which fails with iostat≠0. gfortran prints "Could not open
     specified file for writing." and writes an empty file, but the Python writes the file. So
     upset's save of splot2d/plot3djmol input files differs from the Fortran.
   - plot2d/plot3d are not affected, because they ignore the open's ierr and write to the
     still-connected unit.
   - map3djmol's `open(nout,molfile,'unknown')` after an 'old' open meets the same rule, with the
     same end result.
   - The fix belongs in `units.open`: remember the status and raise `FortranIOError` on a
     conflicting reopen.
2. **`plot_routines.find_plot_par`, `.h01` fallback (package H).**
   - The Fortran calls `get_nterms` without its 5th argument and segfaults whenever the
     SHARM/SDF `.dat` file is missing on the old-format path.
   - The Python carries on and ends with "Error code 2".
   - Files are identical; the exit status and the tail of stdout differ.
3. **`setup_symbols_generic`'s character*256 write of a character*20 actual** (package L): see
   the upset results above. It cannot be reproduced.
4. **Exit status of an uncaught Fortran runtime error.** A runtime error ends the Python with
   status 1 and a traceback; gfortran exits with 2 and prints its "Fortran runtime error"
   message. `programs.run_program` could map an uncaught `FortranIOError` to status 2.
